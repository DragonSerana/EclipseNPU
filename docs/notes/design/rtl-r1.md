### 「同一个沿上同时发生」到底是什么意思

第 4 拍那个"旧的被取走、新的被装进来同时发生"，说的是**逻辑上的同时**，不是物理上的同一纳秒。物理上当然有先后（clock-to-Q 延迟、布线延迟各不相同），你的直觉没错。

同步设计把这件"物理先后"约束到了不影响功能的范围内，靠的是两点：

1. 一个寄存器的 **D 端（将要变成什么）和 Q 端（现在是什么）是两个不同的点**。时钟沿做的事只有一件：**把 D 在沿之前的值抄到 Q 上**。
2. 别的电路在同一个沿读这个 Q，读到的是 **Q 在沿之前的值**（因为 Q 要等 clock-to-Q 延迟之后才变）。

所以第 4 拍实际发生的是：

```
                      沿
                       ↓
s_data    ─────── 55 ─────── 55 ───
reg_data  ─────── 22 ──┐
                       └───── 55 ───
下游在同一个沿采 reg_data → 采到 22（沿之前的值）
本级在同一个沿采 s_data   → 装进 55（沿之前的值）
```

两件事都在**同一个沿**被界定，但各自看的都是"沿之前"的值，所以谁都不影响谁。这就是 §0 实验 2 里 `cnt <= cnt_next` 和 `cnt <= cnt + 1` 结果相同的原因，也是 `<=` 叫"非阻塞"的原因：**右边全部用旧值算完，左边同时更新**。

**"同时"的定义是"同一个时钟沿"，不是"同一纳秒"。沿是一个分界，不是一个瞬间。**

物理上的先后被什么吸收掉了？建立时间约束：

```
T_clock-to-Q + T_组合逻辑 + T_setup ≤ T_周期
```

只要所有路径都满足这条，跨沿的因果关系就成立，沿内部谁先谁后不影响功能；不满足就是时序违规（亚稳态）。**这就是后面 R2/R4 要跑 yosys 综合看 f_max 的原因**——它量的正是这条约束。

## 1. 端口

`s_` = slave 侧，也就是**上游那一侧**，模块在这里**收**数据；`m_` = master 侧，**下游那一侧**，模块在这里**发**数据。这两个前缀来自 AXI 的写法（`s_axis_*` / `m_axis_*`），看别人的代码和波形时通用。

每个接口三根线：`valid`（我有数据）、`ready`（我能收）、`data`（数据本体）。方向规则是固定的，不由模块的视角决定：

- `valid` 和 `data` 同向，**由发送方驱动**；
- `ready` 反向，**由接收方驱动**；
- 一次传输成立 = 在同一个时钟沿上采到 `valid && ready` 同时为 1。

所以本模块对上游是接收方（`s_valid` / `s_data` 是输入，`s_ready` 是输出），对下游是发送方（`m_valid` / `m_data` 是输出，`m_ready` 是输入）。唯一容易记混的地方：**两个 `ready` 的方向都和同侧的 `valid` 相反**。

```
        上游  ──→ s_valid   ┌────────────────┐  m_valid ──→  下游
              ──→ s_data    │ 单级寄存器切片  │  m_data  ──→
              ←── s_ready   └────────────────┘  ←── m_ready
```

| 信号 | 方向 | 位宽 | 含义 |
| --- | --- | --- | --- |
| `clk` | in | 1 | 单时钟域，1 cycle = 1 个 posedge |
| `rst_n` | in | 1 | 同步复位，低有效 |
| `s_valid` | in | 1 | 上游这一拍有数据 |
| `s_data` | in | 8 | 上游送来的数据 |
| `s_ready` | out | 1 | 本级这一拍能收 |
| `m_valid` | out | 1 | 本级这一拍有数据给下游 |
| `m_data` | out | 8 | 送给下游的数据 |
| `m_ready` | in | 1 | 下游这一拍能收 |

## 2. 三条约束（先当规矩用，等 R1.3 撞到问题之后再回来看为什么）

1. `m_valid` / `m_data` 只能由寄存器驱动，**不许看 `m_ready`**；
2. `s_ready` 可以组合地看 `m_ready`（方向是反的，允许）；
3. 只在 `s_valid && s_ready` 那一拍更新寄存器。

### 两个 `ready` 不恒等

最容易混的不是方向，是这一条：`s_ready` 和 `m_ready` **不是同一件事**。`m_ready` 是下游给的**输入**，`s_ready` 是本级算出来的**输出**，方向不同、归属不同。

| 我这边的状态 | 下游这一拍 | `s_ready` |
| --- | --- | --- |
| 空着 | 收不收都行 | 1 |
| 满着 | `m_ready=1` | 1 |
| 满着 | `m_ready=0` | 0 |

即 `s_ready` = "我手空着，**或者**我这一拍就能把东西交出去"。只有在"我满着"时它才等于 `m_ready`；我空着时它恒为 1，跟下游毫无关系。

差的这一点就是**这级寄存器的缓冲能力**——如果这级是纯导线（0 级缓冲），两者才恒等。

另外：`m_ready=1` 的含义是"下游**这一拍**能接"，不是"下游处理完了"。

### 反压（backpressure）

下游把 `ready` 拉低，表示"我这一拍收不了"。这个"收不了"会**沿着 `ready` 线一路往上游传**，逼着上游停下等待——这就是反压。方向是从下游往上游，跟数据流相反。

一条链上的传播过程：

1. 下游 `m_ready=0`；
2. 本级如果手上满着，就交不出去，于是 `s_ready=0`；
3. 上游看到 `s_ready=0`，虽然它有数据（`s_valid=1`），这一拍也交付不了，只能等 `s_ready` 变 1；
4. 上游的上游同理……

它存在的意义：**让流水线里的临时拥堵不丢数据**。如果没有 `ready` 这条线，下游一忙就只能丢数据，或者需要一个无穷大的缓冲。

### 保持（stability）：`valid` 拉高之后不许变

这是握手协议的硬规则（AXI 等协议都写明）：**发送方一旦把 `valid` 拉高，在交付完成（`ready` 也为 1 的那一拍）之前，必须保持 `valid` 为 1、`data` 不变。不能撤，也不能换成下一笔。**

为什么：接收方可以**在任何一拍**采样。它不一定在你 ready 的那一拍才看数据——它可能提前把线上的值记下来、或者用组合逻辑提前判断。发送方中途换数据，这一笔的定义就模糊了，接收方可能拿到一半旧一半新。

这正是 §2 第 1 条（`m_valid` / `m_data` 必须由寄存器驱动）的原因：**寄存器天然保持**——不被更新就一直是原值；而组合逻辑算出来的值下一拍可能就变了，保持不住。

**注意 TB 也要守这条**：TB 扮演上游，`s_valid=1` 且 `s_ready=0` 期间 `s_data` 不许变。做法是把"下一笔要发什么"和"这一拍线上举着什么"分成两个变量，只有交付成功后才换下一笔。
