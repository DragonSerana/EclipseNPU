# R2 设计注记：bank 化 SRAM 与仲裁

> 上游：`docs/plans/rtl-plan.md` §4 R2；`docs/plans/ops-audit.md` §4.2
> 前置：R1（`rtl-r1.md`）的 valid/ready 与反压——R2 的每个端口都要挂 R1 的握手。

## 0. 目标与 done（摘自 rtl-plan §4）

目标：SRAM 做成 4/8 bank（字交织）+ 仲裁 FSM。sequencer 发 DMA 写的同时 MAC 在读，**端口冲突在这里第一次真实发生**。

done：

- bank 冲突 stall 在波形里可见，并与手算对上；
- 能回答"bank 数 / 读端口数怎么决定 `N_tile`"——用端口预算重新推一遍 ops-audit §4.2 那个"400KB < 512KB"的账。

## 1. 三种带宽，别混成一个（框架）

R2 的第一件事是把"带宽"这个词拆开。这里同时存在三条独立的带宽，量级不同、消费者不同：

| # | 带宽 | 谁在拉 | 谁在供 |
| --- | --- | --- | --- |
| ① | **SRAM 读端口** | 16×16 MAC 阵列 | SRAM bank |
| ② | **SRAM 写端口** | DMA 引擎 | — |
| ③ | **DDR ↔ SRAM 搬运** | DMA 引擎 | DDR（行为级模型） |

**关键：① 和 ③ 不是同一个数。** 阵列每拍读多少，跟 DMA 每拍能搬多少，中间隔着"数据复用了多少次"。所以"32 vs 16 的 2× 缺口"能不能成立，取决于复用倍数——这正是本节要算的东西。

## 3. 端口预算（待填）

### 3.1 先把词说清楚

| 词 | 中文 | 一句话 |
| --- | --- | --- |
| fp16 | 半精度浮点 | 2 字节一个数。SRAM 里存的就是它 |
| A / B | 左矩阵 / 右矩阵 | `C = A × B` 的两个输入 |
| M / N / K | 三个维度 | A 是 M×K，B 是 K×N，C 是 M×N |
| PE | 处理单元 | 阵列里一个乘加器，算一个乘积并累加 |
| 16×16 阵列 | — | 256 个 PE，摆成 16 行 16 列 |
| output-stationary | 输出驻留 | 每个 PE 蹲着一个累加器，攒住自己的输出元素，让 A、B 流过它 |
| k 步 | — | 沿 K 那一维的第 k 次累加（`C[i][j]` 要累加 K 次） |
| tile | 瓦片 / 块 | 阵列只有 16×16，128×128 的输出要切成 8×8 块来算 |
| bank | 存储体 | 大 SRAM 拆成若干小片，每片每拍能独立读写一次 |
| arbiter | 仲裁器 | 裁判，决定这一拍谁用哪个 bank |
| stall | 停顿 | 停一拍 |
| 反压 backpressure | — | 停不住就顺着握手线往上顶 |

### 3.2 一拍里到底发生了什么

用 **4×4** 阵列举例（真设计是 16×16，道理一样）。第 k 步，每个 PE 算一个乘积、累加进自己的累加器：

```
        一行的 4 个 PE 共用同一个 A 值     一列的 4 个 PE 共用同一个 B 值

                 B[k][0]   B[k][1]   B[k][2]   B[k][3]
                    │         │         │         │
                    ▼         ▼         ▼         ▼
  A[k][0] ───▶  ┌─────┐   ┌─────┐   ┌─────┐   ┌─────┐
                │ PE  │   │ PE  │   │ PE  │   │ PE  │
  A[k][1] ───▶  ├─────┤   ├─────┤   ├─────┤   ├─────┤
  A[k][2] ───▶  ├─────┤   ├─────┤   ├─────┤   ├─────┤
  A[k][3] ───▶  └─────┘   └─────┘   └─────┘   └─────┘
```

**4×4 阵列一拍要从 SRAM 读 4 个 A + 4 个 B = 8 个数。** 16×16 同理——这就是 Q1。

### 3.3 九个问题

基准场景：一条 `M=128 N=128 K=128` 的 MATMUL（`tests/golden/golden.easm` 里就是 8 条这种）。

| # | 问题 | 结果 |
| --- | --- | --- |
| Q1 | 16×16 阵列，**一拍**（一个 k 步）要从 SRAM 读几个数？ | 16*2,MN并行 |
| Q2 | 一条 128×128×128 的 MATMUL，阵列要跑**多少拍**？ | (128*128)/(16*16)*128|
| Q3 | 这条 MATMUL 的输出要切成**多少个 16×16 的块**？ | (128*128)/(16*16)|
| Q4 | 整条 MATMUL，阵列**一共要从 SRAM 拿多少个数**？ |M*K*(N/16)  +  K*N*(M/16)|
| Q5 | 整条 MATMUL，DMA **一共要往 SRAM 写多少个数**？（A 和 B 各有多少个元素） | 2*128*128|
| Q6 | Q4 ÷ Q5 = **每个数平均被读了几次**（复用倍数） | 8|
| Q7 | Q5 ÷ Q2 = **DMA 平均每拍要搬几个数** | 4|
| Q8 | Q7 对比上限 **16 个数/拍**（`DMA_BYTES_PER_CYCLE=32B`），余量多少？ |4 |
| Q9 | 所以"阵列要 32/拍、DMA 只给 16/拍"这个 **2× 缺口成立吗**？真正卡住的是哪条带宽？ | |

## 4. 参数决策与子步骤

### 4.1 已定的参数（baseline）

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| 存储布局 | A 行主序 `M×K`，B 行主序 `K×N` | 最朴素，先把冲突暴露出来 |
| 字宽 | **1 个数** | 让 bank 算术最干净、冲突最直观 |
| bank 数 | **32** | 阵列要 32 读/拍，每 bank 1 个读口 |
| 端口类型 | **每 bank 1R1W** | 一拍总需求 48 次（32 读 + 16 写），1RW 只给 32，不够 |
| bank 号 | **地址 % 32** | 线性映射，先把问题暴露出来 |

这组参数是**故意选成会冲突的**——done 标准是"看见冲突"，不是"没有冲突"。

### 4.2 子步骤

- **R2.1 单 bank 1R1W**：一块 bank 的行为模型，搞清"同拍读写"、"字宽"、"读不破坏"的语义。手算 + 波形。
- **R2.2 32 bank + 地址映射**：加 bank 数和 `bank = 地址 % 32`。先跑**无冲突**的地址序列，验证数据正确、顺序不乱。
- **R2.3 冲突 + 仲裁** ← **done 标准**：发 A 的跨步访问，看见多路冲突；加仲裁器；stall 在波形里可见并与手算对上。
- **R2.4 三种映射对照**：同一场景跑 (a) `% 32` (b) padding（K→129）(c) XOR 散列，只改地址计算、硬件不动。对照波形与冲突拍数。

### 4.3 范围纪律

**R2 不写 16×16 阵列。** 阵列的"消费者"由 TB 生成地址序列来扮演（呼应 rtl-plan §3"TB 是手写激励"）。阵列本身是 R4。
