## 0. 目标与 done（摘自 rtl-plan §4）

目标：SRAM 做成 4/8 bank（字交织）+ 仲裁 FSM。sequencer 发 DMA 写的同时 MAC 在读，**端口冲突在这里第一次真实发生**。

done：

- bank 冲突 stall 在波形里可见，并与手算对上；
- 能回答"bank 数 / 读端口数怎么决定 `N_tile`"——用端口预算重新推一遍 ops-audit §4.2 那个"400KB < 512KB"的账。

## 1. 三种带宽，别混成一个（框架）

R2 的第一件事是把"带宽"这个词拆开。这里同时存在三条独立的带宽，量级不同、消费者不同：

| # | 带宽 | 谁在拉 | 谁在供 |
| --- | --- | --- | --- |
| ① | **SRAM 读端口** | 16×16 MAC 阵列 | SRAM bank |
| ② | **SRAM 写端口** | DMA 引擎 | — |
| ③ | **DDR ↔ SRAM 搬运** | DMA 引擎 | DDR（行为级模型） |

**关键：① 和 ③ 不是同一个数。** 阵列每拍读多少，跟 DMA 每拍能搬多少，中间隔着"数据复用了多少次"。所以"32 vs 16 的 2× 缺口"能不能成立，取决于复用倍数——这正是本节要算的东西。

## 3. 端口预算（待填）

### 3.1 先把词说清楚

| 词 | 中文 | 一句话 |
| --- | --- | --- |
| fp16 | 半精度浮点 | 2 字节一个数。SRAM 里存的就是它 |
| A / B | 左矩阵 / 右矩阵 | `C = A × B` 的两个输入 |
| M / N / K | 三个维度 | A 是 M×K，B 是 K×N，C 是 M×N |
| PE | 处理单元 | 阵列里一个乘加器，算一个乘积并累加 |
| 16×16 阵列 | — | 256 个 PE，摆成 16 行 16 列 |
| output-stationary | 输出驻留 | 每个 PE 蹲着一个累加器，攒住自己的输出元素，让 A、B 流过它 |
| k 步 | — | 沿 K 那一维的第 k 次累加（`C[i][j]` 要累加 K 次） |
| tile | 瓦片 / 块 | 阵列只有 16×16，128×128 的输出要切成 8×8 块来算 |
| bank | 存储体 | 大 SRAM 拆成若干小片，每片每拍能独立读写一次 |
| arbiter | 仲裁器 | 裁判，决定这一拍谁用哪个 bank |
| stall | 停顿 | 停一拍 |
| 反压 backpressure | — | 停不住就顺着握手线往上顶 |

### 3.2 一拍里到底发生了什么

用 **4×4** 阵列举例（真设计是 16×16，道理一样）。第 k 步，每个 PE 算一个乘积、累加进自己的累加器：

```
        一行的 4 个 PE 共用同一个 A 值     一列的 4 个 PE 共用同一个 B 值

                 B[k][0]   B[k][1]   B[k][2]   B[k][3]
                    │         │         │         │
                    ▼         ▼         ▼         ▼
  A[k][0] ───▶  ┌─────┐   ┌─────┐   ┌─────┐   ┌─────┐
                │ PE  │   │ PE  │   │ PE  │   │ PE  │
  A[k][1] ───▶  ├─────┤   ├─────┤   ├─────┤   ├─────┤
  A[k][2] ───▶  ├─────┤   ├─────┤   ├─────┤   ├─────┤
  A[k][3] ───▶  └─────┘   └─────┘   └─────┘   └─────┘
```

**4×4 阵列一拍要从 SRAM 读 4 个 A + 4 个 B = 8 个数。** 16×16 同理——这就是 Q1。

### 3.3 九个问题

基准场景：一条 `M=128 N=128 K=128` 的 MATMUL（`tests/golden/golden.easm` 里就是 8 条这种）。

| # | 问题 | 结果 |
| --- | --- | --- |
| Q1 | 16×16 阵列，**一拍**（一个 k 步）要从 SRAM 读几个数？ | 16*2,MN并行 |
| Q2 | 一条 128×128×128 的 MATMUL，阵列要跑**多少拍**？ | (128*128)/(16*16)*128|
| Q3 | 这条 MATMUL 的输出要切成**多少个 16×16 的块**？ | (128*128)/(16*16)|
| Q4 | 整条 MATMUL，阵列**一共要从 SRAM 拿多少个数**？ |M*K*(N/16)  +  K*N*(M/16)|
| Q5 | 整条 MATMUL，DMA **一共要往 SRAM 写多少个数**？（A 和 B 各有多少个元素） | 2*128*128|
| Q6 | Q4 ÷ Q5 = **每个数平均被读了几次**（复用倍数） | 8|
| Q7 | Q5 ÷ Q2 = **DMA 平均每拍要搬几个数** | 4|
| Q8 | Q7 对比上限 **16 个数/拍**（`DMA_BYTES_PER_CYCLE=32B`），余量多少？ |4 |
| Q9 | 所以"阵列要 32/拍、DMA 只给 16/拍"这个 **2× 缺口成立吗**？真正卡住的是哪条带宽？ | |

## 4. 参数决策与子步骤

### 4.1 已定的参数（baseline）

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| 存储布局 | A 行主序 `M×K`，B 行主序 `K×N` | 最朴素，先把冲突暴露出来 |
| 字宽 | **1 个数** | 让 bank 算术最干净、冲突最直观 |
| bank 数 | **32** | 阵列要 32 读/拍，每 bank 1 个读口 |
| 端口类型 | **每 bank 1R1W** | 一拍总需求 48 次（32 读 + 16 写），1RW 只给 32，不够 |
| bank 号 | **地址 % 32** | 线性映射，先把问题暴露出来 |

这组参数是**故意选成会冲突的**——done 标准是"看见冲突"，不是"没有冲突"。

### 4.2 子步骤

- **R2.1 单 bank 1R1W**：一块 bank 的行为模型，搞清"同拍读写"、"字宽"、"读不破坏"的语义。手算 + 波形。
- **R2.2 32 bank + 地址映射**：加 bank 数和 `bank = 地址 % 32`。先跑**无冲突**的地址序列，验证数据正确、顺序不乱。
- **R2.3 冲突 + 仲裁** ← **done 标准**：发 A 的跨步访问，看见多路冲突；加仲裁器；stall 在波形里可见并与手算对上。
- **R2.4 三种映射对照**：同一场景跑 (a) `% 32` (b) padding（K→129）(c) XOR 散列，只改地址计算、硬件不动。对照波形与冲突拍数。

### 4.3 范围纪律

**R2 不写 16×16 阵列。** 阵列的"消费者"由 TB 生成地址序列来扮演（呼应 rtl-plan §3"TB 是手写激励"）。阵列本身是 R4。

## 6. R2 结论（2026-10 完成）

代码：`rtl/bank/sram.sv`（一块 bank，1R1W，参数化）、`bank_mem.sv`（32 块并排，读写都 bank 化）、`bank_xbar.sv`（地址拆分 + 路由 + 仲裁，含原 `bank_map` 的冲突计数）。

### 6.1 端口预算：§3 那九个问题的答案

- 阵列一拍要 **32 个数**（16 A + 16 B）→ SRAM 要 32 个读端口 → **32 个 bank**。
- **复用倍数 = 8**（每个数被读 `N/16` 次）→ DMA 平均只要 **4 个数/拍**，上限 16 → **4 倍余量**。
- **所以 §1 里"32 vs 16 的 2× 缺口"不成立，方向也反了**：DMA 不是瓶颈，**SRAM 读端口才是**。
- 一拍总需求 32 读 + 16 写 = 48 次；32 bank × 1R1W = 64 次/拍 → **1R1W 是必须的**（1RW 只给 32，不够）。

### 6.2 冲突与仲裁（R2.3）：done 标准达成

`bank = 地址 % 32`，A 的地址是 `i*128 + k`，而 **`128 % 32 = 0`** → A 的 16 行全落 bank 0。

| 手算 | RTL 实测 |
| --- | --- |
| bank 0 收到 17 个请求（A 的 16 个 + B 的 `j=0`） | `bank_cnt[0] = 17` |
| 全部 grant 需要 **17 拍** | **17 拍** |

两个 17 对上。**两个实现要点：**

1. **`grant` 必须打一拍。** 仲裁是组合的（本拍出结果），sram 读是同步的（下拍出数据）。不打拍 → **数据全对但归属错一格**，波形上很难查。
2. **写侧不用打拍。** 写在这一拍的沿上就完成，没有数据要等。**"打拍"是为了对齐两条路的延迟，不是为了减速。**

### 6.3 三种映射对照（R2.4）

| 场景 | 行主序 `%32` | padding（行距 `K+1`） | XOR（`addr[4:0] ^ addr[9:5]`） |
| --- | --- | --- | --- |
| 只有 A（16 个请求） | **16 拍** | **1 拍** | 2 拍 |
| A + B（32 个请求） | **17 拍** | **2 拍** | 3 拍 |

**四个发现：**

1. **布局就是杠杆。** 同一个访问序列、硬件一行不改，**17 拍 → 1 拍**。
2. **padding 有效是数学保证**：`K+1` 是奇数，和 2 的幂的 bank 数永远互质 → **对任何偶数 K 都有效，不需要针对 pattern 设计**。
3. **XOR 在真实 K 上会完全失效**：ops-audit §4.2 的 `K=1024`，`i` 的信息在 bit 10 以上，而 `addr[9:5]` 窗口在 bit 5~9 → 折下来全是 0。**窗口必须跟着 stride 走**（要修就得折 bit 10~14，但那对 K=128 又失效）。
4. **A/B 互撞 padding 和 XOR 都治不了**：padding 后 A 落 bank 0~15、B 也落 bank 0~15 → 仍然每个 2 个 → 卡在 2 拍。**只能靠分开 operand buffer 解决。**

### 6.4 三条要带走的结论

**① 布局是杠杆，而且它必须由编译器决定。**
只有编译器掌握"哪个下标是行、哪个是列"——**硬件只看地址，分不出来**。所以硬件折位（bank hash）做不对的事，编译器按语义重排（swizzle）能做对：

```
A[i][k] 存到 i*K + (k ^ i)     ← swizzle
bank = (k ^ i) % 32 = k[4:0] ^ i    → 16 个不同 bank ✓
对 K=1024 照样有效，且因为 i≤15 只动低 4 位，bank 内地址不变 → 不浪费容量
```

**② 先 padding 保底，等 tile 形状定了再上 swizzle。**
padding 的定位是"**不用设计、不会错**"；swizzle 是"**不浪费容量，但必须为访问模式设计**"。而现在 `transB` / `accumulate` / 尾块都还没定（R4 的范围）——**在不知道需求全集的情况下设计 swizzle 是白设计**。布局策略要做成编译器里**可替换的一档**（CUTLASS 就是参数化 swizzle 的）。

**③ 存储不是"一块 512KB"，是"几块专用 buffer"。**
A 和 B 必须在不同的 bank 集合上，否则无论怎么调布局都会互撞。这条直接改 ops-audit §4.2 的结论形状。

## 7. 回填主线（本次已做）

### 7.1 `ops-audit.md` §4.2 —— 那笔"400KB < 512KB"的账要补一半

原账只算了**容量**。R2 补上**端口 + 布局**：

- lhs 是跨步读（16 行，行距 K），**`K=1024` 且 bank=32 时 `1024 % 32 = 0`** → 不处理布局就是 16 路冲突；
- lhs 和 rhs 在同一个 bank 空间会互撞（一个跨步、一个连续，R2.4 实测 2 拍而不是 1 拍）；
- **所以"一块 512KB 装 dst+lhs+rhs"在容量上成立、在端口上不成立。** 结论的形状是**分开 operand buffer**（昇腾 L0A/L0B/L0C 的形状），`N_tile` 的选取依据要从"容量够不够"改成"**容量 + 端口预算**"。

### 7.2 `isa.md`

- **内存模型**：加了"packed 不是免费的"（packed = 行主序 = 行距 K = 冲突的来源）和"**布局是编译器的责任，不是硬件的自由**"。
- **cycle 模型**：给"bank 冲突留到后续性能模型"那句加了前提说明——**模型把冲突记为 0，只有在编译器把布局做对的前提下才成立**。

### 7.3 `roadmap.md`

RTL 支线小节加了 R2 的完成状态和 R3 的起点。

### 7.4 还没做的（留给 R4）
